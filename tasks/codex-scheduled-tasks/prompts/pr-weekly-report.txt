时间口径：
- 使用 Asia/Shanghai（北京时间）。每周五上午 10:00 执行。
- 每次开始时固定本次统计截止时间为实际开始执行的时间；起点是本次计划执行日的上一个周五 12:00:00。仅纳入 mergedAt > 起点 且 mergedAt <= 截止时间的 PR。手动试跑也按同一周五周期计算；不要改成最近 7×24 小时。
- 严格保留用户指定的上周五 12 点起点。正常周五 10 点运行与上周五 12 点起点之间存在每周五 10–12 点的统计空档，不擅自改动。
- 只统计已合并 PR；排除未合并、关闭未合并、Draft。统计依据是合并时间，不能用创建时间、更新时间或提交时间替代。

读取与核验：
- 优先通过已连接的 GitHub 插件只读查询上述仓库，完整分页。也可使用本机已登录的 gh CLI 补足查询或分页；不得显示认证信息。

- 把北京时间边界转换为 UTC，先查询时间范围，再用每条 PR 的实际 mergedAt 精确过滤。检查完整数量，避免默认分页或结果上限造成漏项；结果多时按日期拆分查询。

归并和分类：
- FastGPT 与 Pro 不按仓库分别堆砌列表，而是按同一用户功能、同一问题或配套前后端改动合并成一项，保留全部关联 PR 链接与仓库标识。
- 明确区分“新增功能与改进”“Bug 修复”“工程维护、测试与文档”。依据内容判断，不能只按 feat/fix 前缀分类。混合改动可分点说明，统计仍按 PR 去重。
- plugin 单独说明新增能力、Bug 或 SDK 变化；若与 FastGPT/Pro 配套，例如插件国际化，则交代对应关联，避免当成几项互不相关的功能。
- 描述变化带来的行为或用户价值。Bug 写清触发场景、原有问题和修复结果。避免逐提交罗列，不夸大效果，不把 PR 自述的测试当成本次重新验证。
- 包括小修复、测试、文档和依赖更新，不能因为低影响就从完整覆盖中漏掉。可以按功能归并长尾。

报告结构：
- 标题：FastGPT PR 周报（YYYY-MM-DD）。
- 开头标注精确北京时间范围、只统计已合并 PR，并列出 FastGPT、Pro、plugin 的各仓库 PR 数和去重总数。
- 给出 3–5 条本周重点。
- 列出新增功能与改进、Bug 修复、plugin、工程维护/测试/文档，全部使用列表，禁止 Markdown 管道表格、table 组件或其他表格布局。
- FastGPT 与 Pro 按功能归并到共同的业务模块下，必要时先给共同摘要，再逐条列 PR。每个 PR 使用列表项，第一行加粗中文行为摘要，第二行放 PR 链接和对应作者主页链接。不要只写编号，也不要把几个作者放在一起而无法对应 PR。
- 对非主线合并、配套依赖和明确的兼容边界做必要标注；不要把尚未上线写成已发布。
- 核对报告关联 PR 的去重集合与检索集合一致。若正文为了篇幅只展示重点，应追加紧凑的全量 PR 索引，确保所有本期 PR 可追溯。
- 无新增时明确写“本期无已合并 PR”。任一仓库无法访问时写明读取失败及本次覆盖不完整，不能写成 0，不隐瞒缺失，也不凭印象补齐。
- 完整报告写入飞书文档；机器人只发送短概览和文档链接，不再把全部 PR 拆成多条消息或多张卡片。不得创建或修改项目仓库文件，不发送 Slack、邮件或 GitHub 评论。本对话简短确认文档链接与推送结果，失败时如实说明失败阶段。

PR 作者展示：
- 读取并展示每个 PR 的实际作者（author），不能用合并者、assignee、reviewer 或提交者替代。
- 每个 PR 链接旁都标注对应作者。优先展示 GitHub 公开显示名称，同时保留 @login 并链接到作者主页；没有显示名称时只用 @login。不要猜测真实姓名。
- 展示格式示例：[F#123](PR链接) · [作者名（@login）](作者主页)。机器人保留实际账号标识。
- 同一功能合并多个仓库或多个 PR 时，仍保留每个 PR 与作者的准确对应，不仅列一个无法对应的作者合集。正文与全量 PR 索引都遵守此要求。
- 无法取得作者时标注“作者信息未获取”，不能猜测或省略。

飞书短通知（已实测的 Card 2.0 格式）：
- 用户已授权推送至唯一 webhook：<由本机通知脚本读取私有目标>
- 只发送一张简短概览卡片：总 PR 数与各仓库数量、作者数、时间范围、3–4 条重点，以及一个“阅读完整周报”按钮，跳转文档 URL。PR 全量明细留在文档中。
- 外层 {"msg_type":"interactive","card":{...}}；card 必须含 schema:"2.0"、config.update_multi:true、config.width_mode:"default"；正文放在 card.body.elements。不要使用旧 card.elements 或混入 post 节点。
- header 使用蓝色、chart_colorful 图标，显示报告名称和日期。正文使用两个浅灰 column_set/column 分块（概览和重点）加一个 primary_filled、width:"fill" 的 button；button.behaviors 使用 open_url/default_url 指向文档。无需回调或飞书用户登录。
- column_set.flex_mode 用 none，column 用 width:"weighted"、weight:1；padding:"12px"，vertical_spacing:"8px"，背景 grey-50。不要给 column 设置 corner_radius：该 webhook 实测会返回 unknown property。markdown 使用 content、text_size:"normal" 或 "notation"，可用加粗与 grey 辅助文字。
- 保持“标题 → 概览/重点 → 阅读入口”层级，禁止表格。不要把大段 PR 明细、折叠全文或多张分段卡片重新加回通知。
- 最终 JSON 请求体按 UTF-8 字节数校验，控制在 19KB 以内。正常短通知应远小于此限制。
- 仅 HTTP 成功且业务 code=0 才算推送成功；如响应含 StatusCode，也必须为 0。HTTP 200 本身不代表成功。
- 对明确拒绝且未投递的通知，可修复或短暂退避重试，最多 3 次；已成功的不重复推送。网络超时结果不确定时记录不确定状态，避免无限重发或声称成功。
- 创建或写入文档失败时不要推送空文档；若文档成功但通知失败，在本对话提供已完成的文档链接与脱敏错误。
- 不在文档、卡片正文、日志摘要和本对话回执中展示 webhook 或其他密钥。
